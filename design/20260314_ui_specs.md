# 2026-03-14 UI Specifications

## Goal

Convert the current interactive TypeScript CLI into a browser-based UI while preserving the existing output semantics:

- The application remains a local program started on the user's machine.
- The UI is shown in a browser.
- The board output remains text-based.
- The statistics table remains text-based.
- The board and the table must be rendered in a fixed-width font so alignment is preserved.
- The browser must show live progress information and logs while the backend is working.

## High-Level Architecture

The browser UI must be implemented as a thin frontend over a local Node.js backend.

The system must be split into three layers:

1. Shared core logic
2. Local backend API
3. Browser frontend

### 1. Shared Core Logic

The shared core must contain the chess and evaluation logic that is independent of the UI layer.

It should include:

- parsing the initial position from FEN or SAN moves
- resolving position history
- parsing the side to move filter
- parsing the time filter
- evaluating a position using Lichess, Chess.com, and Lichess database data
- merging move statistics
- rendering the unicode board as text
- rendering the statistics table as text
- rendering CSV output

The existing text renderers should remain the source of truth for output formatting:

- `renderBoard(fen): string`
- `renderStatsTable(rows): string`
- `renderStatsCsv(rows, context): string`

The browser UI must display these strings rather than reimplementing board or table layout in HTML tables or custom board widgets.

### 2. Local Backend API

The backend must:

- serve the HTML, CSS, and browser JavaScript
- expose API endpoints used by the browser
- read configuration from `.env`
- access the filesystem and existing local cache/data directories
- call the existing Lichess, Chess.com, and RocksDB-related logic
- emit logs and progress updates during long-running work
- return final evaluation results to the browser

The backend must remain responsible for:

- secrets and tokens
- all external API requests
- cache reads and writes
- CSV export
- all Node-only functionality

The browser must not directly call Lichess or Chess.com.

### 3. Browser Frontend

The browser frontend must use `design/20260314_html_page.html` as the UI basis.

The frontend must:

- use the central content area for assistant/output messages
- use the composer form for user input
- show the user's submitted input as a user message bubble
- show logs, progress, board output, and table output in the assistant area
- preserve the overall look and layout of the current HTML design

## UI Requirements

### General Interaction

The browser UI must support the same functional workflow as the CLI:

1. enter or load usernames
2. enter a position as FEN or SAN moves from the starting position
3. select side
4. optionally enter a time filter
5. submit the request
6. view live logs and progress while data is being collected
7. view the board and merged move table
8. continue by entering SAN moves
9. go backward in move history
10. export CSV
11. force refresh user games when requested

### Output Rendering

The browser must distinguish between plain text output and fixed-width output.

Plain text output includes:

- status summaries
- explanations
- errors
- regular assistant messages

Fixed-width output includes:

- unicode chess board text
- statistics table text
- any other alignment-sensitive output

The board and table must be rendered in elements equivalent to:

```html
<pre class="mono-output"></pre>
```

The fixed-width styling must preserve spaces and line breaks. The font must be a monospaced font such as:

- `Consolas`
- `"Courier New"`
- another platform-appropriate monospace fallback

Required CSS behavior:

- `white-space: pre`
- `overflow-x: auto`
- monospaced font stack

The board and table must not be converted into proportional-font paragraphs.

### Conversation Layout

The assistant output area must support appending multiple message blocks over time.

It must be possible to render a single evaluation cycle as a sequence of assistant blocks, for example:

1. status/log lines
2. progress section
3. board text block
4. FEN text
5. merged statistics table block

The UI may group these visually, but the logs must remain readable in chronological order.

### Progress Display

When the browser sends a request that triggers backend work, the UI must show live progress rather than waiting for a final response.

The browser must show progress for long-running tasks such as:

- Lichess user dump download
- Lichess `data_uci` processing
- Chess.com user dump download
- Chess.com `data_uci` processing

Progress must be displayed as structured browser UI, not raw terminal redraw output.

Each progress item must show:

- label
- current value
- total value
- completion state

Recommended display:

- a label
- a browser progress bar
- numeric text such as `42 / 100`

The frontend must update an existing progress item when new events for the same task arrive.

Suggested stable progress keys:

- `lichess-user-dump`
- `lichess-data-uci`
- `chesscom-user-dump`
- `chesscom-data-uci`

### Log Display

The browser must show live logs emitted by the backend while the request is running.

Logs should include:

- status messages
- request lifecycle messages
- source totals
- warnings
- retry-related messages
- errors

Logs must be appended in chronological order.

The log view must support automatic scrolling to the newest message while a job is active.

The implementation may visually separate logs from final rendered results, but both must be visible in the same evaluation flow.

### History Navigation

The browser UI must support the same conceptual history navigation as the CLI.

Required actions:

- apply a SAN move to continue to a child position
- move back one position in history
- optionally jump to a previous history entry in future versions

The browser does not need to mimic the left-arrow terminal input literally. Instead, it should provide an explicit browser control for going back.

### CSV Export

The UI must support exporting the currently displayed rows to CSV.

The backend must remain responsible for generating the CSV and writing or returning it.

The UI may implement this as:

- a button that triggers a backend export and returns a file
- a button that triggers a backend export to disk and shows the exported path

## API Requirements

### Request Model

The browser should not hold server-side session state for the evaluation job itself. Instead, the browser should send the current input state on each evaluation request.

The submitted state should include at minimum:

- `lichessUser`
- `chessComUser`
- `initialPosition`
- `history`
- `timeFilter`
- `forceRefreshUserGames`

The backend is responsible for resolving the effective FEN from the submitted state.

### Job-Based Execution

Long-running evaluation work must use a job-based model.

Recommended flow:

1. browser sends `POST /api/evaluate`
2. backend creates a job and returns `jobId`
3. browser opens a live event stream for that job
4. backend emits logs, progress events, final result, and completion

This avoids a silent blocking request and allows the browser to display live updates.

### Event Streaming

The preferred mechanism for live updates is Server-Sent Events (SSE).

Recommended endpoint:

- `GET /api/jobs/:jobId/events`

The backend should emit structured JSON events.

Recommended event payload model:

```ts
type UiEvent =
  | { type: 'log'; message: string }
  | { type: 'progress'; key: string; label: string; current: number; total: number; done: boolean }
  | { type: 'result'; fen: string; side: 'white' | 'black'; boardText: string; tableText: string }
  | { type: 'error'; message: string }
  | { type: 'done' };
```

The browser must consume these events incrementally and update the UI in real time.

### Final Result Payload

The final result must contain enough information for the frontend to render the completed output without recomputing anything.

The result should include at minimum:

- resolved `fen`
- resolved `side`
- `boardText`
- `tableText`
- merged rows in structured form if needed for future actions

Optional additional fields:

- source totals
- cache-hit information
- export metadata

### Cancellation

Cancellation is optional for the first version, but the architecture should allow it.

Recommended future endpoint:

- `POST /api/jobs/:jobId/cancel`

## Backend Integration Requirements

The existing callback-driven status and progress hooks should be reused instead of replaced.

Current backend/client callbacks should be adapted so they emit browser events rather than terminal-only output.

This includes:

- general status logging callbacks
- Lichess dump progress callback
- Lichess `data_uci` progress callback
- Chess.com dump progress callback
- Chess.com `data_uci` progress callback

The backend must not depend on terminal progress redraw behavior for the browser implementation.

Instead:

- terminal output remains specific to the CLI mode
- structured progress events are used for the browser mode

## Refactoring Requirements

The current CLI implementation must be refactored so UI-specific behavior is separated from reusable application logic.

The recommended split is:

- shared core services for evaluation and rendering
- CLI-specific adapter
- browser/server-specific adapter

The CLI should become one consumer of the shared core.

The browser backend should become another consumer of the shared core.

The browser implementation must not duplicate the chess evaluation logic already present in the CLI code.

## Non-Functional Requirements

### Preserve Existing Output Semantics

The browser version must preserve the meaning and formatting intent of the current CLI output.

Specifically:

- the unicode board must remain text output
- the statistics table must remain text output
- ordering and sort semantics must stay the same
- numeric formatting must stay the same unless intentionally changed in a separate requirement

### Local-First Operation

The application must continue to run locally on the user's machine.

It is not a hosted web app.

### Security

Secrets such as API tokens must remain on the backend and must not be exposed to browser JavaScript.

### Extensibility

The browser architecture should allow future additions such as:

- cancel button
- richer history UI
- saved sessions
- multi-step output grouping
- downloadable artifacts

## Recommended First Implementation Scope

The first browser UI version should include:

- local backend server
- browser UI based on `20260314_html_page.html`
- submission of evaluation requests from the composer area
- live log streaming
- live structured progress bars
- final board rendering in monospaced text
- final table rendering in monospaced text
- move history continuation
- move-back action through an explicit UI control

The first version does not need:

- WebSocket support
- multi-user support
- browser-side direct external API access
- a graphical chessboard widget
- HTML table replacement for the text table

## Explicit Recommendation

The preferred implementation is:

- a local Node.js server
- a browser frontend based on the existing HTML mockup
- shared evaluation/rendering logic extracted from the CLI
- a job-based API
- Server-Sent Events for logs and progress
- fixed-width `<pre>` rendering for the board and statistics table
